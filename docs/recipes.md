# Recipes: the commonest changes, step by step

Written by QA-5 (independent QA check, 5 Nov 2026, findings R4 and the junior test). Each recipe
lists the steps and the files, in the order you touch them. `docs/code-tour.md` explains how each
part works; this page says what to do. When a recipe is wrong or missing a step, fix it in the same
pull request.

## Find the live version of a SQL function, table or policy

Many functions were redefined in several migrations (one of them 21 times), so the first file you
find is often not the one that runs.

1. Search `supabase/schema.sql`: it is the whole schema as the migrations leave it, generated by
   `npm run schema:gen` and checked by `npm run schema:check` (QA-4). What is there is what runs.
2. To see it in the running local database instead: `npx supabase db reset`, then
   `psql postgresql://postgres:postgres@127.0.0.1:54322/postgres` and `\sf public.<function name>`
   (a function) or `\d+ public.<table name>` (a table and its policies).
3. To find which migration last changed it, search `supabase/migrations/` for
   `create or replace function public.<name>` and take the file with the highest number.
4. Never copy an old migration's version of a function to change it: copy it from
   `supabase/schema.sql`, or you silently undo every later change to it.

## Add a migration

1. `npm run migration:new -- <story_id>_<slug>`, for example `npm run migration:new -- s1_e3_14_dedication`.
   Never `npx supabase migration new`: the versions run ahead of the calendar, and
   `npm run migrations:check` refuses a version older than the newest one on main.
2. Write it by the conventions in `supabase/README.md`: RLS and a commented policy on every new
   table, explicit grants, `set search_path = ''` on functions, a doc comment on each one.
3. A function you change: start from its live text (recipe above).
4. `npx supabase db reset`, then `npm run types:gen` and `npm run schema:gen`. Commit
   `src/lib/database.types.ts` and `supabase/schema.sql` with the migration.
5. Tests: a pgTAP file in `supabase/tests/database/` with an `allowed: <policy>` and a
   `denied: <policy>` test for each new policy (`npm test` checks the names), then
   `npx supabase test db`.

## Add a field to a story, end to end (for example a short dedication)

A story field reaches more places than the settings form. Search for an existing field of the same
kind (for example `completion_status`) across `src/` and `supabase/schema.sql`: every place that
mentions it is a place yours probably needs. The usual list:

| Where | What to change |
| --- | --- |
| Migration | the column on `public.stories` with a check constraint; `create_story()` and `update_my_story()` (from their live text) to accept and check it |
| Who can read it | public reads go through `get_story_page()` and `story_card_json()`; add it there if readers see it. Writes go through the functions, so no new policy is needed for them |
| Staff | `admin_story_settings_json()` and `admin_change_story_settings()` (staff may change settings, never a writer's words, CLAUDE.md rule 18), and `src/features/staff/lib/staffStorySettingsDiff.ts` so the history shows before and after |
| The writer's data | `data_export_tables()` (Download my data) and the story export, so the writer gets everything that is theirs (GDPR art. 15 and 20) |
| Types and schema | `npm run types:gen`, `npm run schema:gen` |
| Front end | `src/schemas/story.ts` (zod), `src/features/writing/hooks/useStorySettingsForm.ts` and `useNewStoryForm.ts`, the form section in `src/features/writing/components/`, the reader's `src/features/reading/api/storyPage.ts` and the component that shows it |
| Words | the field's label and help in `src/locales/ro/writing.json` and `src/locales/en/writing.json` (Romanian with ș and ț), then `npm run i18n:check` |
| Tests | pgTAP for the check constraint and the functions; a Vitest test for the zod schema; the story settings e2e spec |
| Docs | a line in the "Story settings" section of `docs/code-tour.md` |

## Add a setting staff can change

1. A migration inserts the row into `public.settings`: `key`, `value` (jsonb), `is_public` (true
   only when signed-out visitors and members may read it through the table's policy) and a
   `description`. Read it in SQL with `public.setting_value('<key>')`.
2. In the app, read a public setting from the table with the shared client, as
   `fetchNameChangeDays()` in `src/features/account/api/accountNames.ts` does, with a fallback for
   a missing value.
3. Staff change it at `/staff/settings` (`src/features/settings/`): `lib/settingGroups.ts` decides
   which group it shows in. Every change goes through an `admin_*` function and is logged with
   before and after values.
4. Any fallback number in code (used only when the setting can't be read) should say so in a
   comment that names the setting. Search for the old number when you change a default:
   comments that quote it go stale.

## Change a limit that is a setting (for example the comment length)

The comment limit is the setting `comment_max_characters`. Change it at `/staff/settings` on each
environment. The code keeps fallbacks for when the setting can't be read: in SQL inside
`check_comment_text()` and in `src/features/comments/hooks/useCommentLimit.ts`
(`decidedCommentLimits`). Change those too only when the decided default changes, and search
`src/` and `supabase/` for the old number in comments.

## Change wording on a screen

1. The words are in `src/locales/ro/<namespace>.json` and `src/locales/en/<namespace>.json`; the
   namespace is the feature's (for example `notifications.json`). Search both files for the
   current English text to find the key.
2. Change both languages in the same pull request. Robert reads all new Romanian himself.
3. On staging, staff may have overridden that key in Staff › Website › Interface text (S1-E11-18,
   `/staff/website`).
   An override wins over the file, so if your change doesn't show, look there first: it is not a
   bug in your change.
4. Website pages (home page, help, questions, notices) never come from the locale files: their text
   is in the CMS, edited in Staff › Website.
5. Email wording: `src/locales/*/email.json`, also overridable by staff, sent by the one
   `send-email` sender with locked placeholders (S1-E11-19).

## Add a feature folder

Copy the structure of `src/features/comments/` or `src/features/messages/` (api, hooks,
components, a `register<Feature>Translations.ts` that loads its locale files on first use through
`createNamespaceTranslations()` in `src/lib/namespace-translations.ts`, and a README). Member text
(anything a user wrote) is drawn only with `SafeMarkdown` (`src/components/ui/SafeMarkdown.tsx`),
with a preset from `safeMarkdownElements.ts`, and checked on save with `has_html_tag()` and
`has_unsafe_link()` in SQL. Calls that only staff may make go in `api/staff/` inside the feature, so the reader's
download never carries them (QA-5). Don't copy `src/features/writing/` (it predates the pattern)
or `src/features/design-system/` (no api or hooks).

## Compare a screen with its board

`scripts/visual-compare.ts` (LOOK-0) puts each app screen beside the design board render it should
look like, at 1440, 768 and 390 px wide. Every LOOK pull request attaches these pictures.

1. Start the local stack and load the demo stories, so the screens have real-looking content:
   `npx supabase start`, then
   `psql "postgresql://postgres:postgres@127.0.0.1:54322/postgres" -f supabase/staging-topups/demo-content-2a.sql`
   and the same for `demo-content-2b.sql` and `classic-authors.sql`.
2. Start the app: `npm run dev`. It must point at the local stack: put `VITE_SUPABASE_URL` and
   `VITE_SUPABASE_ANON_KEY` from `npx supabase status -o env` (`API_URL` and `ANON_KEY`, public local
   values) in `.env.local`. Without them every signed-in screen fails at the log-in step, because
   the app can't reach the database and the security headers block any other address.
3. Run `npx tsx scripts/visual-compare.ts` for every screen, or name some:
   `npx tsx scripts/visual-compare.ts /discover /library`.
4. The pictures are in `test-results/visual-compare/<width>-<board>.jpg`.

The routes and their boards are listed in `scripts/visual-compare.routes.json`; add a line there
when a new screen gets a board. The script signs in as the seed persona each route names, in
English and the light theme, because the boards are drawn that way.
