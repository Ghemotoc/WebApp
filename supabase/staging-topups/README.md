# Staging top-ups

Small SQL files that bring an existing staging database up to date with a story's changes to `supabase/seed.sql` (decided 18 Oct 2026).

Why: staging already holds the seed personas, so re-loading `seed.sql` there fails on duplicate keys. A fresh database (local, CI, or staging after a full reset) needs no top-ups: `seed.sql` already has everything.

Rules for each file:

- Name: `<story-id>.sql`, for example `S1-E3-01.sql`, written by the story that changed the seed.
- It adds or updates only what that story changed. It never creates accounts and never touches real data.
- It is safe to run twice (`on conflict do nothing`, or `update … where` the value is still missing).
- It starts with a header comment: the story, what it adds, and how to check it worked.
- The pull request lists it under **By hand**. Running it: `docs/runbooks/staging-reset-and-seed.md`, "Top-ups".

`S1-E2.sql` brings a staging database seeded before epic S1-E2 up to date: consents, the four test invites, and the persona usernames and pen name.

`S1-E3-01.sql` adds the three seed stories (two for adult_writer, one for teen_17) and their tags.

## Demo content for the investor demo (Lane B, 23 Oct 2026)

`demo-content-2a.sql` is generated by `npm run demo:build` from `content/demo-stories/*.md` (and `content/classics/texts/*.md` once the classics texts are there): the synthetic stories, their tags and published chapters for the January 2027 investor demo. Edit the story files, run the build, commit both. It also runs locally after `npx supabase db reset`: `psql "$DB_URL" -f supabase/staging-topups/demo-content-2a.sql`.

The SQL Editor refuses the single file as too large, so the build also writes the same top-up as parts in `demo-content-2a/` (`part-01.sql` and on, each under 500 KB, split at statement boundaries by the generator). In the SQL Editor, run the parts in order; each is safe to run twice. Part 01 holds the settings and accounts, the last part ends with the check query. `npm run demo:compare-parts` proves on a fresh local database that the parts and the single file give the same rows.

**The one exception to "never creates accounts"** (Robert, 23 Oct 2026, for this top-up only): it creates the five synthetic writers and the official classics account, exactly as `seed.sql` creates the personas (`@personas.test` addresses, fixed IDs `…-0000000001xx`, the shared test password), because the demo needs writers the personas can't stand in for. Every other rule holds: fixed ids, safe to run twice, never production (it refuses a database without the 16 personas). Merge after S1-E3-03 and S1-E3-06.
